Security

How SecretDrop protects your one-time secret links with zero-knowledge encryption in your browser. Zero-knowledge means that our server stores your secret but never holds a key that could read it. This document covers the website secretdrop.to and our onion service, but not Cloudflare's own systems. Plain words first, with technical details in the expandable boxes for anyone who wants to check them.

Version 1.0, November 2026

In short

  • Your secret is encrypted in your browser before anything is uploaded. Our server only ever receives ciphertext.
  • The key travels inside the link, after the #. It never reaches our server.
  • A secret can be opened exactly once. Then it is deleted. Unopened secrets expire on their own.
  • Every message is padded to the same size, so not even its length is visible.
  • No accounts, no IP logs, no cookies from us, no analytics.
  • You can use SecretDrop entirely inside Tor through our onion service.
  • Like every web app, SecretDrop depends on our server, and on the clearnet site also on Cloudflare, delivering unmodified code. The threat model lists this and the other limits.

1. How a secret travels

  1. You write a message or choose files. Your browser creates a random key and encrypts everything locally.
  2. Only the encrypted data goes to our server, together with a random ID. The key stays with you.
  3. You receive a link. The ID and the key both sit after the #, and only the ID ever reaches our server. You send the link to the recipient.
  4. The recipient opens the link and clicks Retrieve secret. Their browser downloads the encrypted data and decrypts it locally.
  5. Right before our server sends the data, it deletes it. From then on, the link works for nobody.

Link format. https://secretdrop.to/#<id>.<key>. The ID is a random UUID (version 4, 122 random bits) that our server creates with crypto.randomUUID(). The key is 32 random bytes from crypto.getRandomValues(), written as 43 characters of base64url. Everything after the # is called the fragment. JavaScript in your browser reads it, and browsers do not include it in requests to the server. With a password, the link contains only the ID and the password takes the place of the key. The Code tab shows only the part after the #. It opens the secret on secretdrop.to and on our onion service, so it needs the same care as the link.

Creating a secret, step by step.

  1. Your browser creates a random salt. Without a password, it also creates a 256-bit key. With a password, it runs Argon2id on the password and the salt instead.
  2. It packs the content together with its metadata, pads it and encrypts it with AES-256-GCM.
  3. It asks our server for a random ID. The server signs the ID, and the signature works only once and only for two minutes. On the clearnet site, the server checks Turnstile before it hands out the ID. On the onion service, your browser solves a small proof of work for the signed ID instead.
  4. It computes the verification tag for the ID.
  5. It uploads the ciphertext to POST /api/store. The signed ID, the expiry window, the salt and the tag travel in request headers.

Opening a secret, step by step.

  1. Your browser reads the ID and the key from the fragment and checks the format.
  2. After your click, it asks GET /api/auth/<id> for the salt.
  3. It derives the keys, with Argon2id if there is a password, and computes the verification tag.
  4. It sends the tag to POST /api/retrieve/<id>. The server compares it in constant time, deletes the entry and then returns the ciphertext.
  5. Your browser decrypts the ciphertext, removes the padding and shows the content.

2. Encryption

SecretDrop encrypts with AES-256-GCM, a standardized and widely studied cipher. GCM is authenticated encryption: any change to the encrypted data is detected, so nobody can alter a secret without the recipient's browser noticing.

All cryptography runs in your browser through the built-in Web Crypto API, except Argon2id, which runs as WebAssembly. Our server never takes part in encrypting or decrypting.

  • Key derivation. The 256-bit link key, or the Argon2id output for passwords, goes into HKDF-SHA-256 with an empty salt, which is fine because the input is already uniformly random. HKDF derives two independent subkeys with separate labels: secretdrop:aes-gcm-256 for encryption and secretdrop:hmac-auth for the verification tag. No key is used for two purposes.
  • Fresh keys. Every secret gets its own key and a random 96-bit IV, so a key and IV pair is never used twice.
  • Verification tag. Your browser computes HMAC-SHA-256 over the secret ID with the second subkey. The server stores this tag and compares it in constant time when someone retrieves the secret. The tag does not reveal the key. It is a fixed value, though, so anyone with a copy of it could retrieve the secret and thereby destroy it.
  • Randomness. Keys, IVs and salts come from crypto.getRandomValues(), the cryptographically secure random number generator of your browser.

3. Passwords

If you add a password, the link no longer contains a key. The password itself becomes the key, so the link alone is useless to anyone who intercepts it. Send the link and the password through two different channels.

Passwords are processed with Argon2id, a variant of Argon2, the winner of the Password Hashing Competition. Every guess costs 64 MiB of memory and three passes, which makes guessing on a large scale slow and expensive, even with graphics cards.

The create form also protects you from weak choices. It refuses passwords that are too short or too common, and the dice button creates a strong passphrase for you.

  • Argon2id parameters. Memory 64 MiB, 3 iterations, parallelism 1, a 16-byte random salt and 32 bytes of output. The password is normalized to Unicode NFC first, so the same characters always give the same key. The output enters HKDF like a link key. The parameters are fixed in the code.
  • Guessing stays expensive. The verification tag is computed only after Argon2id. Anyone with a copy of our database therefore has to run Argon2id once for every guess.
  • Strength check. Your browser estimates the strength of the password with a simple formula based on its length and the kinds of characters it uses. Below about 40 bits, or when the password is among the 100,000 most common passwords from Have I Been Pwned, it is refused. Simple tricks like 0 for o or a number at the end are recognized. The formula can still rate a predictable password as strong, so for anything important, use the dice. The check runs locally and never sends the password anywhere.
  • No hint from the download. The list is loaded for everyone who opens the create form, not only for people who type a password. Fetching it reveals nothing. If the list cannot be loaded, a secret with a password is not created.
  • Dice passphrases. Five words from the EFF short word list with 1,296 words, about 52 bits. Each word is picked with crypto.getRandomValues() and rejection sampling, so every word is equally likely.
  • WebAssembly. Secrets without a password do not need WebAssembly and also work in Tor Browser on the Safer level.

4. What the server stores

For each secret, our server keeps exactly six things. All of them are deleted together, after the retrieval or when the secret expires.

StoredWhy it is needed
Random IDfinds the right entry
Encrypted datathe secret itself, unreadable without the link
Random saltturns a password into a key. Secrets without a password get one too, so both look the same
Verification tagchecks a retrieval without our server learning the key
Attempt counterdeletes the secret after five wrong attempts
Expiry time, rounded up to the next ten minutesdeletes the secret on time and shows the creation time only to within ten minutes

It never receives your key, your password, the content, file names, file types or the number of files, and it stores no IP addresses. Without the link it cannot be read, and apart from a short version header and its padded size it looks like random bytes.

The database has one table with exactly these columns and a second table with a single number, the total size of all stored data. A copy of it would show how many secrets exist, their padded sizes, their rounded expiry times, failed attempts and the order in which they were created. It would not show any content, keys, names or IP addresses.

5. Hiding metadata

Encryption hides the content. Metadata can still say a lot: how long a message is, what a file is called, where a photo was taken. SecretDrop hides as much of it as it can.

  • Every message, and every set of files up to 32 KB, is padded to exactly the same size before encryption. A one-word password and a long letter look identical.
  • Larger uploads are rounded up to fixed steps. They grow by at most about 6 percent below 64 KB and about 3 percent above. Only the approximate size stays visible, never the exact number of bytes.
  • File names and file types are encrypted together with the content. By default, the recipient also sees a random file name instead of the original, with the file extension kept.
  • By default, JPEG, PNG and WebP images are cleaned before encryption, which removes location, camera and other EXIF data. If that fails, nothing is uploaded. Other image formats are only sent once you turn this option off, and other files are sent unchanged.
  • The stored data does not show whether a password was set. Only the timing of the requests can hint at it.
  • Byte layout. Each frame starts with a 4-byte big-endian length, followed by the header {"v":5}, the 12-byte IV and the ciphertext with its 16-byte GCM tag. Type, item lengths, file names and MIME types are inside the encrypted part.
  • Version header. The header is not covered by the GCM authentication. Changing it cannot reveal or alter a secret. At most, it makes decryption fail.
  • Padding. Content up to 32,768 bytes is padded to 32,768 bytes, so every message is sent and stored as exactly 32,807 bytes. Messages are limited to 10,000 characters, which always fits. Above that, sizes are rounded up with the Padmé scheme, which leaves only about 320 possible sizes between 32 KB and 50 MB.
  • Same pattern. The browser always creates a salt and makes the same requests in the same order, with or without a password. Only the time Argon2id needs between them differs.
  • Image cleaning. The browser cuts the metadata out of the file and keeps only what is needed to display the image, plus the rotation of JPEG photos. Everything else is dropped, including unknown parts, color profiles, embedded previews and data appended after the image. The image data itself is not changed, so there is no quality loss. If the cleaned image does not open as a test, the upload stops with a notice instead of sending the original. Remove sensitive metadata from documents yourself.
  • Time zone. The expiry time shown to you is calculated in your browser. Our server never learns your time zone.

6. Retrieval and deletion

  • Our server deletes a secret right before it sends the data. If the download breaks off, the secret is gone and the sender has to create a new one.
  • Opening a link does not use up the secret. It is only fetched when someone clicks Retrieve secret, so link previews in messengers and automated email scanners cannot destroy it.
  • After five wrong attempts, the secret is deleted.
  • Unopened messages expire after 1 hour to 7 days, files after 1 hour to 3 days, as chosen by the sender. Because expiry times are rounded up, a secret can stay up to ten minutes longer.
  • There are no backups and no copies on other machines.
  • After the secret is retrieved, the page removes the key from the address bar. Coming back with the back button does not show the secret again.
  • Messages are always shown as plain text. Received files are never displayed as web pages, so a file cannot run code on our site. Images and videos get a preview, text files are shown as plain text, and everything else is offered as a download.
  • To delete a secret before it is read, open the link yourself and retrieve it.
  • If a secret is already gone although it should still be valid, assume that someone else has opened it. Nobody can put it back under the same link, because IDs come only from our server and each one can be filled only once.
  • Overwriting. Deleted entries are overwritten in the database file instead of just being marked as free. The database's change log is truncated after every retrieval and every minute, and the memory buffers our code holds are zeroed. Like on any disk, copies of the ciphertext can remain in free space until they are overwritten. The disk encryption protects them while the server is switched off, not against someone with access to the running system.
  • Attempts. A wrong verification tag raises the counter. After five wrong attempts, the entry is deleted. A malformed link is detected in your browser before it contacts the server, so it costs nothing. A wrong password does count.
  • Cleanup. Every minute, our server deletes all secrets whose time is up. It cannot tell messages from files by looking at the data, but every message has the same fixed size. Anything well above that size can only be a file, and the server never keeps it longer than 3 days, even if a longer time is requested.
  • Clean start. All input fields are emptied when the page loads, so a browser cannot restore an old message or password.
  • Limits. Up to 50 MB and 10 files per secret.

7. No logs, no tracking

  • Our web server writes no access logs and discards error logs. The backend writes no logs at all.
  • IP addresses are kept only in the server's memory, for short-lived rate limits against abuse, and are never written to disk.
  • On the clearnet site, every request passes through Cloudflare, which may keep its own logs and set its own technical cookies. The onion service avoids Cloudflare completely.
  • No sign-up, no email address, no cookies from us, no analytics, no tracking pixels.
  • Your browser keeps only your language and theme choice, in session storage, which is cleared when you close the tab.
  • On the clearnet site, Cloudflare Turnstile checks that you are human. It is the only script from a third-party server, and it loads only when you start writing a secret. The onion service has none.
  • Apart from Turnstile, every file comes from our own server. There are no external fonts, images or libraries.
  • The QR code for your link is drawn in your browser. The link is never sent to a QR service.
  • Turnstile and your keys. The Turnstile script can read the page it runs on. It therefore never runs while a secret is opened: it does not load while a secret link is open, the page reloads into a clean state before the retrieve form appears if Turnstile was loaded, and any retrieved secret is cleared before Turnstile loads. On the clearnet create page it does share the page with your message and the finished link, so there you also rely on Cloudflare.
  • Self-hosted libraries. We serve our own copies of argon2.js and qrcode.min.js. They are byte-identical to the published releases and listed with their licenses in licenses.txt.
  • Readable encryption code. Key generation, key derivation, encryption and decryption are in a single file, /js/crypto.js, which you can open and read in your browser.

8. Network and server

  • HTTPS only, enforced with HSTS for one year, including all subdomains.
  • On the clearnet site, your browser connects to Cloudflare with TLS 1.2 or 1.3, and with post-quantum key exchange (X25519MLKEM768) if it supports it. Our server supports post-quantum key exchange as well, for the connection from Cloudflare.
  • A strict Content Security Policy: scripts only from our own origin, plus Turnstile on the clearnet create page. No inline scripts, no plugins, no embedding in other sites.
  • A CAA record limits which certificate authorities may issue certificates for our domain, and we are alerted when a new certificate for it appears in the public Certificate Transparency logs.
  • The API accepts only well-formed IDs, and browsers let only our own pages read its answers. Its error messages are short and reveal nothing about the server.
  • The backend runs as an unprivileged user in a strict sandbox. Its outgoing connections are limited to what the anti-abuse check needs.
  • The server's disk, including its swap space, is fully encrypted, which protects it while the server is switched off, and crash dumps are disabled.
  • Headers on every page. Content-Security-Policy with object-src 'none', base-uri 'none', form-action 'none' and frame-ancestors 'none'. Also X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy no-referrer, a Permissions-Policy that turns off camera, microphone and location, and Cross-Origin-Opener-Policy with Cross-Origin-Embedder-Policy for cross-origin isolation.
  • Cloudflare to our server. This connection is encrypted as well and uses a certificate that Cloudflare checks strictly. In return, Cloudflare has to show our server a client certificate that only our Cloudflare account holds, so our server turns away requests from any other Cloudflare account.
  • Sandbox. No new privileges, a read-only system, no access to home directories or devices, a private temporary directory, protected kernel settings, a filtered set of system calls and no capabilities.
  • Rate limits. Every API endpoint has its own limit.

Our onion service lets you create and open secrets without ever leaving the Tor network. There is no Cloudflare, no DNS lookup and no exit node in between.

  • Tor defense. The onion service has Tor's built-in proof-of-work defense turned on. When it is under heavy load, Tor lets clients that solve a small proof of work connect first.

10. Quantum safety

Future quantum computers threaten public-key cryptography such as RSA and elliptic curves. The encryption of your secret uses none of it. The key travels inside the link, so there is no key exchange that a quantum computer could break.

  • Grover's algorithm, the best known quantum attack on ciphers like AES, at most halves the effective key length. A 256-bit key keeps about 128 bits of security, which is why our link keys are a full 256 bits.
  • HKDF and HMAC with SHA-256 are hash-based and not broken by any known quantum attack.
  • On the clearnet site, Cloudflare uses post-quantum key exchange with browsers that support it, and our server supports it for the connection from Cloudflare. This protects connections against being recorded now and decrypted later.
  • Connections to our onion service rely on Tor's own encryption. Tor is introducing post-quantum key exchange step by step, but onion services do not use it throughout yet.
  • Even without it, a recorded connection contains only ciphertext. Reading it later would also need the link, or for a secret with a password, guessing the password offline.
  • For passwords, quantum computers do not change the basic rule: a strong password, like a dice passphrase, stays strong.

11. Threat model

This model assumes that you opened the real secretdrop.to or our onion address and that your browser works as intended.

SecretDrop protects you from:

  • People on your network, such as a public Wi-Fi or your internet provider. They see only encrypted traffic.
  • Cloudflare and our own server, as long as they deliver our code unchanged. Both only ever handle ciphertext and never see a key or a password.
  • Someone who seizes or copies our database. Without the links, the data cannot be read. Secrets with a strong password stay protected by Argon2id.
  • Link previews and email scanners. They cannot use up a secret, because retrieval needs a click.
  • Spell check and text prediction in your browser. Some browsers send typed text to their maker, such as Chrome with enhanced spell check and Edge with Microsoft Editor or text prediction. Our page turns both off in all its fields, so neither your message nor a pasted key is sent there.
  • Someone who reads a link on its way. They cannot open the secret unnoticed, because the recipient would then find it gone. With a password, the link alone is worthless.

SecretDrop cannot protect you from:

  • A compromised server or Cloudflare. Whoever controls our server, or Cloudflare on the clearnet site, could deliver modified JavaScript that leaks keys. No web-based tool can rule this out completely, and a change aimed at a single visitor would be hard to notice. The onion service takes Cloudflare out of the picture.
  • Turnstile on the clearnet create page. Cloudflare's script runs next to your message and the finished link. Use the onion service if you do not want to rely on it.
  • A compromised device. Malware, or browser extensions that can read every page, can also read your secret.
  • What Cloudflare sees. On the clearnet site, Cloudflare sees IP addresses, times, browser details, the secret ID and the encrypted data, so it can link sender and recipient. It never sees keys or passwords.
  • Guessing weak passwords. Secrets without a password cannot be guessed. With a password, someone holding a copy of our database, or Cloudflare, could try guesses offline. Argon2id makes every guess expensive, but only a strong password, such as a dice passphrase, keeps guessing out of reach.
  • Destroying a secret. Anyone who knows the ID can check whether a secret still exists and destroy it with five wrong attempts. Cloudflare on the clearnet site and anyone with a copy of our database also know its verification tag, so they could retrieve it and thereby destroy it. None of them can read it.
  • The channel you use. Anyone who can read the chat or email that carries the link can open the secret first. If they can also change your messages, they can pass on a new link with the same content, and the recipient would not notice. For sensitive secrets, add a password and send it through a second channel.
  • Your clipboard and history. A copied link or password stays in your clipboard until you copy something else. Your browser may also remember a link you opened, so if you do not retrieve a secret right away, open the link in a private window.
  • The size of large files. Rounding hides only the exact size. The approximate size stays visible.
  • The recipient. What the recipient does with the secret, for example screenshots or copies, is outside our control.

12. Transparency and verification

  • Our warrant canary is updated every month, signed with our PGP key and tied to a recent Bitcoin block, so it cannot have been written in advance.
  • Our PGP key is used for signatures and encrypted contact.
  • Our browser code is served as plain files, not minified or bundled. Only the two libraries are minified, and they match their published releases byte for byte.
  • The full source code of this site and our server is public on GitHub. You can compare it with the files your browser loads.
  • You can check it yourself: open the developer tools of your browser and watch the network tab while you create a secret. Only the ciphertext, the ID, the salt, the verification tag, the chosen expiry window and the anti-abuse token leave your device.
  • Security reports are welcome. Contact details are in security.txt.
  • SecretDrop has not been audited by a third party so far. This document and our public source code are meant to make your own review possible.

14. Glossary

  • AES-256-GCM. A standard cipher that encrypts data and also detects any tampering.
  • Argon2id. A function that turns a password into a key and makes every guess slow and memory-hungry.
  • Ciphertext. Encrypted data. Without the key it cannot be read.
  • Clearnet. The normal internet outside Tor. Here, secretdrop.to behind Cloudflare.
  • Fragment. The part of a link after the #. Browsers keep it to themselves and do not send it to servers.
  • Onion service. A website reachable only through Tor. Neither side learns the IP address of the other.
  • Padding. Filler added before encryption, so that different secrets look the same size.
  • Post-quantum. Cryptography designed to stay secure even against future quantum computers.
  • Proof of work. A small computing task your browser solves before it creates a secret. It stops simple scripts.
  • Salt. Random bytes that make the key derived from a password unique to one secret.
  • Verification tag. A value derived from the key that lets our server check a retrieval without learning the key.
  • Warrant canary. A regularly renewed, signed statement about legal requests. If it is not updated on time, assume that something is wrong.
  • Zero-knowledge. Our server stores your secret but never holds a key that could read it.
