Frequently Asked Questions

Everything you might want to know about encryption, privacy, and how SecretDrop works.

Getting Started

SecretDrop is a free, zero-knowledge service for sharing one-time encrypted messages and files. You write a secret, get a unique link, and share it with the recipient. After it has been read once, or once the expiration window has passed, the secret is permanently destroyed.

The service is designed so that even we cannot read your secret. All encryption happens in your browser before anything reaches our server.

1. You type a secret (and optionally a password) into your browser.
2. Your browser generates a random key (or derives one from your password with Argon2id) and encrypts the secret with AES-256-GCM.
3. Only encrypted data is uploaded to our server, plus a random salt and a verification tag. Neither contains your key or password. The random key stays in the URL fragment (#…) and never reaches our server.
4. The recipient opens the link, their browser decrypts the content locally, and the server destroys the ciphertext.

The full technical picture is on our Security page.

Security & Encryption

We use AES-256-GCM for authenticated symmetric encryption. Secrets without a password get a random 256-bit key, expanded with HKDF. With a password, the key is derived from it with Argon2id (memory: 64 MiB, iterations: 3, parallelism: 1). AES-GCM and HKDF run via the browser's Web Crypto API, Argon2id via WebAssembly. All three are widely studied, standardized algorithms.

The verification tag the server stores is computed only after Argon2id. So every password guess has to run Argon2id once, even for someone with a copy of our database. A five-word passphrase from the dice button (about 52 bits) makes that impractical. A short or common password does not, so the site refuses those. The check runs in your browser against a list we host ourselves.

Random values (IVs, salts, keys) come from crypto.getRandomValues(), a cryptographically secure RNG.

It means the server cannot read what it stores and never sees a decryption key or password. Without a password, the key is in the URL fragment (the part after #), which is processed entirely client-side and is not transmitted in HTTP requests. With a password, your browser derives the key from it.

Even if our server were compromised or seized, the stored secrets could not be read without the key from the link or the password.

No. We have no technical way to decrypt your secret. We never receive the password, the derived key or the key from the link. The AES-GCM authentication tag also makes it impossible to silently modify the ciphertext without detection. We can't even tell how long it is: every message is padded to the same size before encryption, and files are rounded up so only their approximate size remains visible.

With a password, the link no longer contains a key. The password itself becomes the key, so if the link leaks (forwarded chat, screenshot, browser history), the secret stays unreadable without the separately shared password.

Storage & Lifetime

You choose the expiration window when creating the secret. It ranges from 1 hour up to 7 days for messages and up to 3 days for files. After that, the entry is automatically deleted from our database, even if it was never retrieved.

A secret is also destroyed immediately after the first successful retrieval.

Files & Media

Yes. You can attach up to 10 files with a combined size of 50 MB. For larger files, upload them to a storage service (ideally encrypted first) and use SecretDrop to share the download link and any password as a one-time secret.

All file names are encrypted in your browser, so our server never sees them either way. The Anonymize file names option is on by default. It also replaces the name the recipient sees with a random one, and only the file extension stays.

Turn it off if the recipient needs the original names.

Yes, when Remove image metadata is enabled (the default). Before encryption, your browser cuts the metadata out of the image file, such as EXIF, GPS location, camera details, color profiles and embedded previews. Only what is needed to display the image is kept, including the rotation of JPEG photos so they stay upright. The picture itself is not touched, so there is no quality loss and the dimensions are unchanged.

Supported formats are JPEG, PNG and WebP. Other image formats such as HEIC, GIF or AVIF can't be cleaned this way, so nothing is uploaded until you turn the option off.

This applies to images only: other file types (PDFs, documents, …) are uploaded unchanged, so strip sensitive metadata from those yourself first.

Trust & Verification

The full source code of this site and our server is on GitHub ↗. You can read it and compare the files of the site with what your browser loads. What runs on our server cannot be checked from outside. That is why the encryption happens in your browser, where you can check it.

Open your browser's developer tools (Network & Sources tab) and inspect what's actually sent. You will see that only the encrypted data and a few technical values (the ID, salt, verification tag, expiry window and anti-abuse token) leave your device, never the password or the key.

A strict Content-Security-Policy limits code to our own origin. On the Tor onion service it allows nothing third-party at all. On the clearnet site it also allows the Cloudflare Turnstile bot-check. That is the single third-party script, and you can avoid it entirely by using the onion service.

The open-source libraries we host ourselves (Argon2 and the QR code generator), the dice word list and the common password list are listed with their licenses in licenses.txt.
